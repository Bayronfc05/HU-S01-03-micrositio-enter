Introducción

En este sitio vas a aprender exactamente qué pasa entre el momento en que escribes una URL y ves la página.

Vamos a explorar los 9 pasos del viaje completo de una petición web.

Los 9 pasos

  1. 1. El navegador revisa su caché

    Antes de pedir nada a internet, el navegador revisa si ya guardó una copia de esa página o de sus archivos (CSS, imágenes) en tu propio computador, de una visita anterior. A esto se le llama caché: una copia local guardada para no tener que descargar todo de nuevo cada vez.

    El navegador (Chrome, Firefox, Brave, etc.), sin necesitar internet para este paso.

    Es como revisar si ya tienes una fotocopia de un documento en tu cajón antes de ir a la fotocopiadora otra vez.

  2. 2. Resolución DNS

    Si no hay nada en caché, el navegador necesita saber a qué dirección IP conectarse, porque los computadores no entienden nombres como "google.com", solo números. El sistema DNS traduce ese nombre a una dirección IP real.

    Tu sistema operativo consulta primero su propia caché, y si no tiene la respuesta, se la pide a un servidor DNS (normalmente el de tu proveedor de internet).

    Es como buscar el número de teléfono de alguien en la agenda de contactos antes de poder llamarlo: no memorizas números, memorizas nombres, y algo se encarga de la traducción.

  3. 3. Conexión TCP (handshake de 3 vías)

    Antes de mandar cualquier dato, tu computador y el servidor necesitan "saludarse" y confirmar que ambos están listos para hablar. Este saludo tiene 3 pasos: tu computador envía un mensaje llamado SYN (quiero conectarme), el servidor responde con SYN-ACK (recibido, yo también quiero), y tu computador confirma con ACK (perfecto, empecemos). Recién ahí queda abierta una conexión confiable.

    El sistema operativo de tu computador y el servidor de destino, a nivel de red (protocolo TCP).

    Es como cuando llamas a alguien por teléfono: "¿hola, me escuchas?" → "sí, te escucho, ¿y tú a mí?" → "sí, perfecto" — recién ahí empiezan la conversación real.

  4. 4. Handshake TLS y verificación del certificado

    Si el sitio usa HTTPS (como el tuyo), después de la conexión TCP hay un segundo saludo, esta vez para cifrar la comunicación. Tu navegador y el servidor se ponen de acuerdo en cómo van a encriptar los datos, y el servidor le muestra a tu navegador un certificado que prueba que es realmente quien dice ser (emitido por una entidad de confianza, como Let's Encrypt).

    El navegador verifica el certificado; el servidor lo presenta.

    Es como pedirle su cédula a alguien antes de contarle un secreto: primero confirmas que es quien dice ser, y de paso acuerdan un "código secreto" que solo ustedes dos van a entender durante la conversación.

  5. 5. Envío del request HTTP GET

    Con la conexión abierta y segura, el navegador finalmente envía la petición real: un mensaje HTTP pidiendo la página específica que quieres ver. El método GET significa "dame esto", a diferencia de otros métodos como POST que sirven para enviar datos (por ejemplo, un formulario).

    El navegador arma y envía esta petición.

    Es como entrar a un restaurante y decirle al mesero exactamente qué plato del menú quieres.

  6. 6. El servidor procesa y responde con un código de estado

    El servidor recibe la petición, busca lo que le pidieron, y responde con el contenido más un código de estado que resume qué pasó: 200 si todo salió bien, 404 si no encontró la página, 500 si algo falló del lado del servidor, entre otros.

    El servidor de destino (en mi caso, la infraestructura de GitHub Pages).

    Es como cuando el mesero vuelve de la cocina: o te trae el plato (200), o te dice "eso ya no está en el menú" (404), o "hubo un problema en la cocina" (500).

  7. 7. El navegador recibe el HTML y lo parsea

    El navegador recibe el código HTML como puro texto, y necesita convertirlo en una estructura que pueda entender y mostrar. A este proceso se le llama parsear: leer el texto y armar con él un árbol de elementos (llamado DOM) que representa la página.

    El navegador.

    Es como recibir instrucciones de armado de un mueble en texto plano, y a partir de ahí ir entendiendo qué pieza va conectada con cuál, para poder armar el mueble real.

  8. 8. Descarga de recursos: CSS, imágenes, fuentes

    Mientras arma esa estructura, el navegador se encuentra con referencias a otros archivos que la página necesita (una hoja de estilos CSS, imágenes, tipografías), y los pide por separado, cada uno con su propia petición HTTP (repitiendo, para cada uno, algo parecido a los pasos 3 a 7).

    El navegador, haciendo varias peticiones adicionales.

    Es como armar ese mueble y darte cuenta de que faltan piezas: mandas a pedir cada una por separado antes de poder terminar.

  9. 9. Renderizado y pintado en pantalla

    Con el HTML ya estructurado y el CSS ya descargado, el navegador calcula dónde va cada elemento en la pantalla (tamaños, posiciones, colores), y finalmente "pinta" todo eso en píxeles reales que tú puedes ver.

    El navegador.

    Es como tener ya todas las piezas del mueble y las instrucciones claras, y por fin armarlo y ponerlo en el lugar donde vive en la casa — ahí es cuando realmente "existe" para ti.
